Blueline Architecture

Approve the delta, not the download. A release-diff review desk for the package install line — renders every release as a proof sheet and demands sign-off before the byte runs.

Subject
Release-diff review desk
Core
Rust binary + Node shim
Registry v1
npm / npx only
License
MIT (CLI + engine)

Hard rule: nothing executes until judged. Tarballs are fetched to a sandbox temp dir, extracted read-only, diffed, scored — the package is never run, and npm install is only ever invoked after an explicit approve. Note: the README lists the "Diff rendering engine (Rust)" as done, but as of the initial commit only README, LICENSE, and brand assets exist. The engine is a design target, not shipped code.

Part I · System overview

One engine, four doors

A single Rust binary is reached through the CLI, the Node shim, CI, and the MCP hook.

Node shim (@blueline/cli). A tiny npm package. Its bin is a JS launcher that resolves/installs the platform-specific Rust binary (via per-platform optional deps @blueline/binary-{linux,darwin,win}-{x64,arm64}) and execs it. Rust does all heavy lifting; Node only provides the npx ergonomics and PATH registration. The Rust binary is also directly installable (cargo install / direct download) for non-Node environments.

Registry trait. npm is the only implementation now, but the trait (fetch_manifest, fetch_tarball, list_versions) exists from commit 1 so PyPI/cargo plug in later without refactoring the engine.

Part II · Decisions

Key technical decisions

Ten locked choices behind the wedge, each with its rationale.

#DecisionRationale
#D1DecisionRust core + Node shimRationaleSecurity-critical path in a memory-safe, single-binary language; Node only for npx ergonomics.
#D2DecisionLocal deterministic heuristic firstRationaleTransparent, auditable, offline. Hosted ML refines score when token present — never required. Keeps "the wedge stays open" honest.
#D3Decisionnpm-only, Registry trait seamRationaleDeepen one registry; avoid speculative multi-registry code now.
#D4DecisionRead-only sandbox extractionRationaleCore safety invariant. Tarball never executed; only bytes read.
#D5DecisionBaseline = last known-clean versionRationaleSource: locally installed version in node_modules → else previous version in registry list (neutral verdict on first sighting). Overrides persisted in SQLite.
#D6DecisionRevocation = OSV + GitHub Advisory cacheRationaleReuse the open vulnerability corpus; paid tier adds human-verified recall (hosted index).
#D7DecisionStable Verdict JSON schemaRationaleSame struct feeds CLI card, CI comment, and MCP tool. One source of truth.
#D8DecisionNo default telemetry in OSSRationalePrivacy-by-default; hosted tier reports only with explicit token.
#D9DecisionSigned, SLSA-built release binariesRationaleWe audit supply chains — we must eat our own dog food.
#D10DecisionPolicy-as-code (blueline.toml)RationalePer-project + global thresholds, allow/blocklists, required-provenance flags.

Part III · Verdict & heuristics

How a delta is judged

Four severity bands, then the local rule set that feeds them.

  • LOWauto-approveClean delta within policy thresholds — the path that does not block the developer.
  • MEDIUMflagHeuristic score in the caution band; surface reasons, let the human decide.
  • HIGHescalateStrong risk signal; route to a senior engineer for sign-off before install.
  • BLOCKhard failNew postinstall/preinstall script, known revocation, or unpinned dangerous delta.

Heuristic rule set local · v1

  • New executable/binaries (executable bit, .exe, native bindings)
  • scripts field additions (postinstall, preinstall, etc.)
  • New/changed dependencies (transitive risk)
  • Install-script presence
  • Obfuscated / base64 / eval in diff
  • Maintainer/author change vs baseline
  • Semver-major with large delta
  • Missing/forged provenance (surfaced, not auto-fail)
  • Revocation hit (BLOCK)

Provenance is surfaceed, never trusted. The TanStack/router worm shipped valid SLSA L3 attestation — a signature is not a verdict.

MCP design agent hook

Explicit review_install tool (agent calls before install) is primary; optional invasive PATH shim that routes npm/npx through blueline is secondary. Recommend the explicit tool to avoid breaking agent toolchains.

Part V · Open risks

What still needs a call

Three gaps to decide before Phase 1 ships.

First-sighting bootstrap

No baseline on initial install → default to a neutral verdict and flag "no known-clean baseline" rather than BLOCK.

scripts false positives

Legit packages (esbuild, core-js) use postinstall. Need an allowlist-by-maintainer or "review once, remember" flow.

Lockfile vs manifest

review diffs a single package; ci must diff the whole lockfile. Two code paths — ci is Phase 3, not Phase 1.
