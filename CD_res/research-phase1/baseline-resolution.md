# Baseline resolution research

Research for Phase 1's last item, "Baseline known-clean resolution" (design decision D5 in `ARCHITECTURE.md`). D5 says: baseline = last known-clean version; source priority is locally installed version in `node_modules` → else previous version in the npm registry version list → neutral verdict on first sighting. This report tests that plan against npm registry semantics, lockfile/`node_modules` reality, how other tools keep trusted baselines, first-install risk, and baseline-poisoning traps. It ends with a concrete v1 algorithm, a `store.rs` schema change, and poisoning controls.

Empirical checks against `registry.npmjs.org` on 2026-08-13 are flagged inline; the rest is cited.

## 1. npm registry metadata semantics

The full packument at `GET https://registry.npmjs.org/<pkg>` (no `Accept` header, or `application/json`) is a CouchDB document with top-level `name`, `_id`, `_rev`, `dist-tags`, `versions`, `time`, `maintainers`, `users`, and the hoisted latest-version fields. `dist-tags` maps tag names to version strings and "every package will have a `latest` tag defined". `time` maps each version string to its ISO 8601 publish timestamp plus two special keys, `created` and `modified`. `versions` maps every version string to a full version object whose `dist` object carries `tarball`, `shasum`, `integrity` (since Apr 2017, `<algo>-<base64>` SRI), `fileCount`, `unpackedSize`, and the newer `signatures` array (https://github.com/npm/registry/blob/main/docs/responses/package-metadata.md).

The abbreviated ("corgi") packument, returned for `Accept: application/vnd.npm.install-v1+json`, exists to be small enough for installs and contains only `name`, `modified`, `dist-tags`, and `versions` at top level. It deliberately omits `time` (same doc). Verified empirically: `curl -H "Accept: application/vnd.npm.install-v1+json" https://registry.npmjs.org/express` returns top-level keys `dist-tags`, `modified`, `name`, `versions` and no `time`; the per-version `dist` object does include `signatures`, `integrity`, `fileCount`, `unpackedSize`, `shasum`, `tarball`. This matters twice for Blueline: publish-time ordering is impossible from the corgi doc Blueline already fetches (`src/registry/npm.rs` line 14 sends the corgi accept header), and registry signature verification is possible from corgi because `dist.signatures` is present.

The per-version endpoint `GET /<pkg>/<version>` returns the single-version manifest. Verified empirically: `https://registry.npmjs.org/express/4.21.2` returns 200; `https://registry.npmjs.org/express/9.9.9` returns 404. The registry API docs describe this endpoint with `version` being "a version number or `latest`" (https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md).

How npm resolves a spec. `npm-pick-manifest` is "a standalone implementation of npm's semver range resolution algorithm" and is what pacote/arborist use (https://github.com/npm/npm-pick-manifest). Only `tag`, `range`, and `version` selectors are supported. For a tag: take the version the tag points at. For a version: take it exactly. For a range: first, if the `defaultTag` (default `latest`) version satisfies the range and passes the engines/deprecation/staged heuristics, take it; otherwise sort all candidate versions by, in order: not in the `avoid` range, not policy-restricted, published over staged, not deprecated with satisfied engines, satisfied engines, not deprecated, then "higher SemVer precedence over lower SemVer precedence" (https://github.com/npm/npm-pick-manifest). The final tiebreak is semver precedence, not publish time. `pacote.resolve` wraps the same logic and takes a `before` option ("only consider packages published before" a date), which is the one place `time` from the *full* packument is used (https://github.com/npm/pacote/blob/main/README.md).

So the reliable way to compute "the previous version" is to sort the `versions` keys by semver precedence with the `semver` crate (which implements the spec ordering in https://semver.org/) and take the highest version strictly below the target. Publish time is both unavailable in corgi and not what npm uses for ordering; using it would diverge from what npm itself would resolve. npm's own "version-maturity" style tools, like `npq`, implement "suggest the highest older semver outside the recency window" (https://github.com/lirantal/npq), i.e. they also order by semver, not by publish clock.

Gotchas confirmed by research and by the registry itself:

- `time` can be missing or incomplete. npm CLI has needed a fix for `npm view` crashing when `time` is absent (https://github.com/npm/cli/pull/8241). If Blueline ever needs publish age it must tolerate a missing `time`, which again argues for semver ordering as the default.
- Unpublished ("yanked") versions are removed from `versions` and their tarballs 404, but `time` retains them. The unpublish policy is explicit: "package@version is unique, and cannot be reused by unpublishing and re-publishing it", and unpublished versions are deleted from the registry (https://docs.npmjs.org/policies/unpublish, https://docs.npmjs.com/unpublishing-packages-from-the-registry/). The npm CLI issue https://github.com/npm/cli/issues/5058 shows users discovering "unpublished versions" that still appear in `npm view <pkg> time` with old timestamps while being absent from `versions`. Verified empirically: express's full packument has 318 entries in `time` (minus `created`/`modified`) versus 288 entries in `versions`, i.e. about 30 versions exist only as `time` ghosts. Practical consequence: "previous version" must be computed from `versions`, never from `time`; a yanked version can never be selected as a baseline, and if the target itself was yanked, `resolve` already fails closed with "no version" (the registry per-version endpoint 404s).
- `dist-tags.latest` is a publisher-controlled mutable pointer, not an ordering. A publisher can point `latest` at a prerelease or move it at will (https://docs.npmjs.com/cli/v10/commands/npm-dist-tag). npm-pick-manifest treats tags as top-priority selections, not as sort keys. Blueline must not use `latest` for baseline ordering.
- Prerelease ordering: semver precedence puts `1.0.0-alpha` < `1.0.0-alpha.1` < `1.0.0-beta.2` < `1.0.0`, and `0.9.9` < `1.0.0` (https://semver.org). npm range matching excludes prereleases unless a range explicitly includes them. A baseline selector that ignores prereleases matches npm's own default behavior.
- Lexicographic string sorting is wrong for version lists. The current helper `list_versions` in `src/registry/npm.rs` sorts keys with `BTreeMap` order (lines 132-141), which puts `10.0.0` before `9.0.0`. Baseline selection must compare `semver::Version` values.

## 2. Local `node_modules` baseline

The naive approach, read `node_modules/<name>/package.json` and take `version`, works for the flat hoisted layout of npm v3+ and yarn classic, and for scoped names the path is `node_modules/@scope/pkg`. It breaks in the real layouts:

- Hoisted vs nested: npm dedupes to a flat top-level `node_modules` but nests conflicting versions at `node_modules/<parent>/node_modules/<child>`. A bare read finds whichever physical copy happens to be at the top; it does not answer "which version does this project actually resolve". npm documents this as a first-class problem: `npm ls` "shows the logical dependency graph as a tree... without using `npm ls -l`, it became impossible to show where a package was actually installed" (https://docs.npmjs.com/cli/v10/commands/npm-ls).
- pnpm layout: `node_modules/<name>` is a symlink into `node_modules/.pnpm/<name>@<version>/node_modules/<name>`, and every file is a hard link into a content-addressable store (https://pnpm.io/symlinked-node-modules-structure). Reading `package.json` through the symlink yields the right `version`, but a CLI must resolve symlinks, and the physical tree does not look like a flat `node_modules`.
- Multiple versions of the same name can be installed simultaneously (npm nesting, pnpm peer-variant suffixes like `/react-dom@18.2.0(react@18.2.0)`), so "the installed version" is ambiguous without the dependency graph (https://safeguard.sh/resources/blog/how-snyk-parses-npm-yarn-and-pnpm-lockfiles-differently-to-resolve-exact-versions).
- `node_modules` can be missing (fresh clone, `npm ci` not yet run) or stale relative to the lockfile.

The robust options:

- Lockfile as the authoritative source. `package-lock.json` v3 (npm 9+) is a flat `packages` map keyed by literal install path (`node_modules/foo`, `node_modules/@scope/pkg`, `node_modules/foo/node_modules/bar`), each entry carrying `version`, `resolved` (tarball URL) and `integrity` (sha512 SRI); v3 drops the legacy nested `dependencies` tree entirely, making the `packages` map the single source of truth and rejecting sha1 (https://docs.npmjs.com/cli/v10/configuring-npm/package-lock-json/, https://safeguard.sh/resources/blog/npm-lockfile-v3-security-improvements). npm also writes a hidden v3 lockfile at `node_modules/.package-lock.json` (https://docs.npmjs.com/cli/v8/configuring-npm/package-lock-json/), which is a snapshot of the tree actually installed. FOSSA and Snyk both branch on `lockfileVersion` before choosing a parse strategy and read the flat `packages` map when present because it is "authoritative and cheaper to traverse" (https://docs.fossa.com/docs/project-setup/supported-languages/nodejs/npm-lockfile, https://safeguard.sh/resources/blog/how-snyk-parses-npm-yarn-and-pnpm-lockfiles-differently-to-resolve-exact-versions). pnpm's `pnpm-lock.yaml` records the same sha512 plus the tarball URL, with inline resolved dependencies (https://www.subresource-integrity.com/supply-chain-auditing-dependency-verification/lockfile-mapping-analysis/). The lockfile is the only source that binds name + version + integrity together, which is exactly what a baseline needs, and it is path-stable so the same version keeps a stable location across diffs.
- `npm ls --json`. It prints "all the versions of packages that are installed" and accepts a package spec; with `--package-lock-only` it reads the tree from the lockfile instead of `node_modules` (https://docs.npmjs.com/cli/v10/commands/npm-ls). It has two costs: it spawns npm (fine, Blueline already ships a Node shim) and it is known to be slow on large trees. One ecosystem tool notes `npm list` "requires `node_modules` as it loads the actual tree rather than the virtual one" (https://github.com/npm/rfcs/issues/372), which is a real constraint in CI right after a clone.

Recommendation for a Rust CLI reading a project: parse `package-lock.json` (v2/v3 `packages` map, v1 nested `dependencies` fallback) or `pnpm-lock.yaml` first and take the entry for the top-level path `node_modules/<name>`; fall back to `node_modules/<name>/package.json` (resolving symlinks) only when no lockfile exists; treat `npm ls` as an expensive last resort. The lockfile entry also gives the `integrity` needed to cross-check the known-clean store, which the bare `package.json` read cannot.

## 3. Known-clean stores in the wild

`npq` audits before install with pluggable "marshalls": known vulnerabilities, install scripts, typosquatting, package age, and a `min-release-age` style version-maturity check ("will show an error if the specific version being installed was published less than 7 days ago" and "suggests the highest older semver" outside its recency window). It makes a point-in-time decision, delegates the install to npm/yarn/pnpm, and keeps no persistent allowlist (https://www.npmjs.com/package/npq, https://github.com/lirantal/npq). Its author and reviewers are candid about the limit: "npq makes a point-in-time decision based on available data. If a package is compromised or malicious after passing checks, npq cannot retroactively detect or block it" (https://dev.co/security/open-source/npq). That is the boundary between a pre-install gate and a baseline: a baseline must be re-checkable, a gate is not.

`audit-ci` implements the allowlist pattern with three record shapes: module (`axios`, suppresses advisories directly caused by the module, not transitive), advisory (`GHSA-...`), and path (`GHSA-...|full>dependency>path`, with wildcard support), plus per-record `active`, `expiry`, and `notes` fields (https://github.com/IBM/audit-ci). Two documented failure modes matter for Blueline: (a) advisory identifiers were unstable, with npm reindexing advisories daily and breaking previously ignored entries, fixed by moving to stable GHSA identifiers (https://github.com/naugtur/npm-audit-resolver/issues/56, https://github.com/IBM/audit-ci/issues/211); (b) the dependency-path matching silently broke between npm 6 and npm 7/8 audit output, so the same allowlist stopped matching (https://github.com/IBM/audit-ci/issues/213). Lesson: whatever identity a baseline record keys on must be stable and version-bound.

`npm-audit-resolver` is the closest existing "decision store". Its `audit-resolv.json` records each decision keyed by `<advisory>|<dependency-path>` with `madeAt` and `expiresAt`, and the core design principle is precision: "The vulnerability is ignored not on the package level, but a specific path in dependency tree and if the same vulnerable package surfaces elsewhere, potentially as a dependency of a dependency where it does get called in production code, the warning needs to come back" (https://github.com/npm/rfcs/pull/18). The npm RFC for it was never merged (https://github.com/npm/rfcs/pull/18). Blueline's `known_clean` table is structurally the inverse (it records positive evidence for a specific version) but the same discipline applies: key on the exact thing reviewed, and let changed context re-surface the finding.

`Socket` is the most explicit about release-level trust. Its cool-down policy flags package versions whose publish date falls inside a configurable window and states the threat model directly: "New releases concentrate the highest supply chain risk: maintainer account takeovers, malware, and regrettable changes are most often caught and reverted in the first days after publication" (https://docs.socket.dev/docs/cool-down-policy.md). Its alert-resolution system lets an org override alerts with three scopes: a single version (`pkg:maven/io.example/foo@1.2.3`), all versions of a package (`@*`), or a whole vendor group, with `monitor` vs `ignore` actions (same doc). Its baseline presets run from "Essential" (block malware only) to "Comprehensive" (block critical CVEs and risky sources), i.e. even Socket's most aggressive preset blocks known-bad, not unknown-new (https://docs.socket.dev/docs/baseline-presets.md).

`pnpm` ships two controls that together are the closest analog to Blueline's baseline. `allowBuilds` is a per-package allowlist for `postinstall` scripts, explicitly recommended over global re-enable, on the reasoning that "if a dependency did not require a build in the past, it won't suddenly run a malicious script if a compromised version is published" (https://pnpm.io/supply-chain-security). `trustPolicy no-downgrade` fails the install when a package's trust level decreases relative to its earlier releases, e.g. "previously published by a trusted publisher but now only has provenance or no trust evidence", with `trustPolicyExclude` and `trustPolicyIgnoreAfter` to handle false positives (https://pnpm.io/supply-chain-security). That is a per-release baseline against prior releases, exactly D5's shape, and it is enforced as a hard failure.

npm's own signing and provenance give the verification half. Registry signatures live in each version's `dist.signatures`, the signed payload is the template `${package.name}@${package.version}:${package.dist.integrity}`, and the public keys are at `<registry>/-/npm/v1/keys`; `npm audit signatures` verifies them and `npm install --audit-signatures` enforces them (https://docs.npmjs.com/verifying-registry-signatures/, https://docs.npmjs.com/cli/v10/commands/npm-audit/). Provenance attestations add a Sigstore-signed SLSA statement binding the tarball to a source repo, commit, and CI workflow; npm is explicit that provenance "does not guarantee the package has no malicious code. Instead, npm provenance provides a verifiable link to the package's source code and build instructions" (https://docs.npmjs.com/generating-provenance-statements/, https://github.blog/security/supply-chain-security/introducing-npm-package-provenance/). The TanStack compromise in 2025 was "the first documented case of malicious npm packages carrying valid SLSA Build Level 3 attestations", which is the standing argument that provenance is necessary but not sufficient and cannot substitute for a human-reviewed baseline (https://www.janbrennenstuhl.eu/automatic-dependency-updates/). This is Blueline's stated position too: provenance is surfaced, never trusted as sufficient (ARCHITECTURE, D9-area table, "provenance ... surfaced, never trusted as sufficient").

Design patterns that generalize: (1) every allowlist decision is scoped (version, path, or advisory), never name-only, and expires; (2) known-bad is blockable automatically while unknown-new is warnable; (3) the value being "trusted" is an immutable artifact identity (name + version + integrity), not a mutable label like `latest` or a package name; (4) re-checkability beats point-in-time gating.

## 4. First-sighting bootstrap

Blueline's ARCHITECTURE risk list says first sighting should be a neutral verdict with a "no known-clean baseline" flag rather than BLOCK (ARCHITECTURE.md §4). Is that defensible?

The strongest argument against neutrality is the empirical record of "fine for years, then pwned". ua-parser-js was a decade-old package with millions of weekly downloads; on 22 Oct 2021 its maintainer's npm account was hijacked and three malicious versions (0.7.29, 0.8.0, 1.0.0) were published that added a `preinstall` script dropping a Monero miner and a Windows credential-stealing trojan; the compromise lasted roughly four hours and was caught the same day (https://github.com/faisalman/ua-parser-js/issues/536, https://cloud.google.com/blog/topics/threat-intelligence/supply-chain-node-js, https://www.cisa.gov/news-events/alerts/2021/10/22/malware-discovered-popular-npm-package-ua-parser-js). The same UNC3379 actor hit `coa` and `rc` weeks later (Mandiant, same link). The Mandiant write-up's mitigation advice for consumers is verbatim the baseline concept: "Consider locking version numbers of packages to prevent from auto-installing a new package that may be malicious" and "Make sure the installed ... package version is [the last good one]" (same link). A first install of a *new version of a known package* is precisely the highest-risk event (maintainer account takeover of an established package). Socket's cool-down doc and the OpenSSF dependency firewall doc say the same: "A familiar package name can therefore distribute a hostile update. Security controls should evaluate every version rather than permanently trusting a package based on its historical reputation" (https://openssf.org/blog/2026/07/28/what-is-a-dependency-firewall/).

But there are two distinct first sightings and they have different risk profiles, which D5 already encodes. First install of a *brand-new package* has no previous version to diff at all; the only available review object is the entire tarball, and Blueline already treats the full tarball as untrusted, integrity-verifies it fail-closed before extraction, and runs its heuristic review over all of it. First install of a *new version of a known package* has a previous version (installed or from the registry list), which is what D5's first two sources provide. Neutrality is only about the *baseline side of the diff*, not about the target: the target still gets full integrity verification, full extraction review, and a verdict. So "neutral verdict + no-known-clean-baseline flag" is defensible as the baseline input to the diff; it is not a pass.

The wider ecosystem supports warn-not-block as the default posture for "not-yet-known" while it moves to stricter install-time defaults only for specifically dangerous things. npm's `min-release-age` shipped in v11.10.0 but was off by default, and the proposal to default it to 3 days was explicitly not merged as a breaking change (https://github.com/npm/cli/pull/9173); npm v12 plans to make install scripts opt-in, and pnpm defaults `minimumReleaseAge` to 1 day in v11 (https://pnpm.io/supply-chain-security). The OpenSSF's dependency firewall framing says newly published packages "present elevated uncertainty" and that "A minimum package-age policy creates a waiting period", while immediately cautioning that "Package age should not be treated as proof of safety. It is a risk-reduction mechanism that limits exposure during the most uncertain period" (https://openssf.org/blog/2026/07/28/what-is-a-dependency-firewall/). Sonatype's argument against cooldowns is the mirror image and is the clearest statement of the neutrality trap: "A package that is 24 hours old is not automatically safe. Neither is one that is 30 days old. Age may reduce one class of risk, but it does not establish integrity" and "cooldowns can buy time. They cannot create trust" (https://www.sonatype.com/blog/software-dependency-cooldowns-are-a-symptom-not-a-strategy). The same article endorses the Blueline-shaped remedy: "The real question is not 'How long should every dependency sit in timeout?' It is, 'Which releases deserve trust, and which ones should be stopped?'" A neutral first-sighting verdict with an explicit flag is the honest answer to that question when no evidence exists either way, provided the flag is loud and the whole-package review is not skipped. One practitioner analysis makes the complementary point that a neutral default plus re-checking beats a hard block that gets tuned off: "teams tune it down, exempt their own scope, or turn it off on the repos where the friction bites... You end up either too loose to stop a patient attacker or too tight to ship" (https://arrangeactassert.com/posts/minimum-release-age-is-necessary-but-not-enough/).

Security practitioners also flag the alert-fatigue failure mode of over-gating: USENIX research on software composition analysis found developers "ignore vulnerability alerts because of being overwhelmed by them", that "a lot of the SCA vulnerability alerts do not pose a direct threat or impact to their application", and that some users report SCA giving "a false sense of security" because it only covers known vulnerabilities (https://www.usenix.org/system/files/usenixsecurity25-lin-elizabeth.pdf). A tool that BLOCKs every first sighting would inherit both failure modes: it would be bypassed, and it would imply that non-blocked packages are safe. Neutral + flag + full review avoids implying safety.

Conclusion: D5's neutral first-sighting verdict is defensible and matches ecosystem practice, with two non-negotiable conditions: (1) the "no known-clean baseline" state is surfaced explicitly on the card and in JSON, and (2) a first sighting means the entire tarball is the review subject, not nothing. Separately, the risk profile difference between "new package" and "new version of a known package" argues for treating the existence of any prior version (installed or in the registry list) as a strict improvement in review quality: with a baseline, the delta gets reviewed; without one, the whole artifact does.

## 5. Baseline poisoning

The trust-acquiescence trap is real in the current code. `src/review.rs` line 43-48 records `known_clean` unconditionally after extraction and hash verification, using whatever `dist.integrity` the registry reported, before any verdict is even computed. A user who reviews a backdoored version and approves it (or in Phase 0, merely runs `review`) permanently marks that exact tarball "known-clean", and it then becomes the baseline the next diff is measured against. The delta lies if its baseline lies. `store.rs` even has a test, `upsert_refreshes_integrity`, asserting that re-recording the same `(name, version)` with a different integrity silently overwrites the old one. That is the exact shape of a poisoning primitive: whatever the registry says today wins, including a republished or mirrored tarball that swapped bytes under the same version string.

The research points to concrete controls:

- Record what was verified, not what was approved. The signed registry payload is `${name}@${version}:${dist.integrity}` (https://docs.npmjs.com/verifying-registry-signatures/), i.e. npm itself treats name + version + integrity as the identity of a release. Blueline's store already keys on `(name, version)`; it must bind the integrity too and treat a changed integrity for the same `(name, version)` as a discrepancy, never a silent update.
- Pin approve conservatively, deny permissively. npm's accepted RFC for `allowScripts` states the asymmetric rule: "Denials are always recorded name-only... since pinning a denial to a specific version would silently allow a future version to run scripts again. This is intentional: pinning is conservative for approve and permissive for deny", and it rejects semver ranges in approvals because "a range like `nx@<21.6.4` would automatically trust future versions that haven't been reviewed" (https://github.com/npm/rfcs/blob/main/accepted/0054-make-scripts-install-opt-in.md). The known-clean mirror: a record binds one version and one integrity, never a name-only or range entry, so a version bump always requires a fresh review. A clean entry pinned to version `A` must not imply anything about version `B`.
- Key with precision so context changes re-surface the finding. The npm-audit-resolver principle is "ignore the exact path, and if the same vulnerable package surfaces elsewhere the warning needs to come back" (https://github.com/npm/rfcs/pull/18). For Blueline, a known-clean record for `(name, version, integrity)` must not be treated as a clean verdict for the same version number if the integrity differs, nor for any other version, nor after a revocation is published against it.
- Make suppressions expire or get re-checked. Allowlist guides converge on expiry: "a suppression added during an incident that quietly becomes permanent" is "the most common failure of allowlists", entries carry "an owner, a justification, and an expiry date", and "the gate script treats an expired expires date exactly like a fresh finding" (https://www.security-threat.com/supply-chain-dependency-security/dependency-scanning-ci-gates/). For a known-clean baseline the lightest defensible form is re-verification at use time: every time a baseline is consumed, confirm the version still exists in the registry packument and that the registry's current `dist.integrity` still equals the stored one. That is one corgi request, no tarball download, and it catches registry-side mutation of a previously reviewed release.
- "Known-clean" is a cache, not a judgment. The OpenSSF firewall framing and the assured-repository critiques both warn against permanent trust delegated to any list: "you're still trusting trust... This does not automatically make the package malware-free; think of assured software instead as a vetted release and review process" (https://thenewstack.io/zero-cve-supply-chain-risk/). Sonatype's position is the same for cooldowns and by extension for any time- or age-based baseline (https://www.sonatype.com/blog/software-dependency-cooldowns-are-a-symptom-not-a-strategy). A `known_clean` row is evidence that a specific tarball was reviewed on a specific date with a specific verdict; it is not a property of the package. Blueline's own tagline ("Approve the delta, not the download") only survives if the baseline endpoint of the delta is known to be the previously reviewed artifact, so the record must be inspectable and revocable.
- Allowlist fatigue is the adjacent failure: the USENIX SCA study documents alert fatigue causing developers to ignore alerts (https://www.usenix.org/system/files/usenixsecurity25-lin-elizabeth.pdf), and the "cap exception age, require an owner, report allowlist size as a tracked metric so the debt stays visible" advice (https://www.security-threat.com/supply-chain-dependency-security/dependency-scanning-ci-gates/) applies to a growing `known_clean` table too. A store that only ever grows, with no way to see what it silently vouches for, is debt. For v1 this means every read of a baseline should be able to say when it was reviewed and with what verdict.

## Recommendations for Blueline

### Baseline resolution algorithm (v1)

Input: `review <name>@<version>` with an exact resolved target `v`. Baseline is the "last known-clean" release below the target, resolved in this priority order:

1. **Project-resolved version.** If the project has a lockfile, parse it: `package-lock.json` (prefer the `packages` map for `lockfileVersion` >= 2, fall back to nested `dependencies` for v1; keys like `node_modules/<name>` and `node_modules/@scope/pkg`) or `pnpm-lock.yaml`. Take the entry whose key is the top-level path `node_modules/<name>`; its `version` is the baseline. This also yields `integrity` for cross-checking the store. If no lockfile exists, read `node_modules/<name>/package.json` (resolving symlinks for pnpm) as a fallback. If the resolved version equals the target, there is nothing to diff; surface that and exit neutral.
2. **Previously reviewed clean version from the store.** If the project offers no version, take the highest `version` in the `known_clean` store with `verdict = 'clean'` and `version < v` (semver comparison). This is the strongest evidence available because that artifact was actually reviewed by this user/team.
3. **Previous registry version.** Otherwise fetch the packument (corgi is sufficient because `versions` is present and `time` is not needed), parse every key with `semver::Version`, and take the highest version strictly below `v`. Exclude prereleases unless `v` itself is a prerelease (npm's own range semantics). Unpublished versions are already absent from `versions`, so they can never be picked. Do not use `time`, `dist-tags`, or lexical sort. This is the D5 "previous version in the registry list" source.
4. **First sighting.** If no version below `v` exists in any source, there is no baseline: verdict is neutral with the explicit flag `no_known_clean_baseline = true`, and the review subject is the entire tarball (which is still integrity-verified fail-closed and fully extracted before any verdict).

Baseline integrity cross-check: when the baseline comes from step 1 or 2 and a store record exists for that `(name, version)`, compare integrities. The store's `integrity` should match the lockfile's `integrity` (step 1) or is the record itself (step 2). Mismatch, or a store record whose stored integrity no longer matches the registry's current `dist.integrity` for that version, is a fail-closed discrepancy flag, not a silent re-record.

Edge cases handled: unpublished/yanked versions (absent from `versions`, never selected; a yanked target already fails `resolve`), prereleases (excluded unless the target is a prerelease), scoped packages (`@scope/pkg` in lockfile keys and percent-encoded `%2f` in the packument path, both already handled by path construction in `npm.rs`), `0.x` vs `1.x` (semver ordering, `0.9.9 < 1.0.0`), multiple installed versions (the lockfile top-level path entry is the direct/project resolution; nested copies under `node_modules/<parent>/...` are not candidates), missing `time` (irrelevant, ordering is semver), and dist-tag moves (tags never used for baseline ordering).

### SQLite schema (`src/store.rs`)

The current table already keys on `(name, version)` with `integrity` and `reviewed_at`, which is the right spine. Phase 1 changes:

- Add a `verdict` column (`TEXT NOT NULL DEFAULT 'pending'`). A row becomes a usable baseline only when `verdict = 'clean'`. Do not backfill; Phase 0 rows stay 'pending' and are never treated as baselines until re-reviewed.
- Change `record_known_clean` into `record_review(name, version, integrity, verdict)` and gate it: only LOW verdicts (the auto-approve band) write `verdict = 'clean'`. No verdict means no clean record.
- Remove the overwrite-on-different-integrity behavior. On conflict, insert a *new* row keyed `(name, version, integrity)` or fail with a discrepancy error; the current `upsert_refreshes_integrity` test encodes the poisoning primitive and must be replaced by a test asserting that a changed integrity does not silently replace the stored one.
- Keep `reviewed_at`; add nothing else in v1 (no reviewer identity, no expiry, no source column). The cheapest re-verification is at read time: when a baseline row is consumed, compare its `integrity` to the registry's current `dist.integrity` for that version (one corgi fetch) and to the lockfile's `integrity` when available.

`src/review.rs` must stop recording on every run: move the store write to after the verdict is computed, and pass the verdict in. The Phase 0 behavior of recording "this exact tarball, integrity-verified" is fine as a *cache* only when it is labeled as a review-with-verdict, never as an approval of the package.

### Preventing baseline poisoning (v1)

1. Record facts, not approvals: `(name, version, integrity, verdict, reviewed_at)`. The rendered card should say "previously reviewed clean on <date>", not "known clean".
2. Bind integrity: a known-clean row is `(name, version, integrity)`; any change to integrity for the same `(name, version)` is a discrepancy and fails closed.
3. Never write name-only or range entries; never derive a baseline from `latest` or any dist-tag.
4. Re-verify at use time: baseline consumption always cross-checks integrity against the registry packument (and the lockfile when the baseline is project-local). This is the "cache, not judgment" discipline and it also catches a republished or mirrored artifact.
5. Revocation wins: a later OSV/GitHub-advisory hit against a stored version must override the clean record at read time. Phase 2 concern; the schema needs no new column for it if revocation is checked before a baseline is consumed.
6. First sighting stays loud: `no_known_clean_baseline` is part of the JSON verdict output, not a prose note, so CI and the MCP tool can react to it.

### YAGNI statement

Smallest defensible v1: (a) baseline resolution as the four-step priority above using `package-lock.json`/`node_modules`, the store, and corgi packument semver ordering; (b) a `verdict` column and gated, non-overwriting store writes; (c) read-time integrity cross-check against the registry. Explicitly deferred: expiry/rotation of records, reviewer identity, publish-age heuristics (npq-style recency, Socket cool-down), `npm ls` execution, provenance-based baseline qualification, and store cleanup tooling. The one non-deferrable correction to Phase 0 is removing the unconditional auto-record in `review.rs` and the overwrite semantics in `store.rs`, because both are baseline-poisoning paths.

## Adversarial self-check

- Could "highest semver below target" pick a version that was never reviewed? Yes, in step 3 it is registry-suggested, not store-backed. It is still a legitimate D5 "previous registry version" baseline for diffing; the diff quality is the guarantee, and the store cross-check only binds integrity when a record exists. If reviewers want stronger guarantees, the baseline card should state whether the baseline came from the project, the store, or the registry.
- Does excluding prereleases break legitimate flows? A team pinned to a prerelease target (`next` tags) would get step 3 failing to find a baseline and fall to first sighting. That is safe (loud flag, full-artifact review), just noisier. Acceptable for v1; a refinement could allow the immediately preceding prerelease of the same `major.minor.patch` when the target is a prerelease.
- Does "neutral on first sighting" contradict fail-closed? No: fail-closed applies to integrity, extraction, and verification boundaries, which all still hard-fail. Neutral applies only to the baseline input of the diff. The report's condition is that the flag is machine-readable.
- Is the store cross-check enough against a registry-compromised republish of the same version? The read-time corgi comparison catches an integrity change for a version already in the store; for a brand-new version there is no record to compare, which is exactly the first-sighting case. Nothing short of re-downloading every baseline would close that completely; v1 accepts it and the delta review is the backstop.
- Does removing the upsert-overwrite break any legitimate flow? Republishing the same `(name, version)` with different bytes is not legitimate; npm itself forbids reusing a `name@version` (https://docs.npmjs.org/policies/unpublish). The only legitimate path is the store gaining a new record for a genuinely new version.
- Is step 2 (store as baseline) safe when the store record predates a revocation? No, and the recommendation says revocation must be checked before a baseline is consumed. If that check is accidentally dropped in Phase 1, the store could vouch for a revoked version. The read-time cross-check plus revocation check are both mandatory at the consumption site, and the `verdict` column must not be read as approval of any other version or of the package generally.
